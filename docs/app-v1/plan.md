# Dance Count for Ballroom — アプリ化 v1 計画

## Context（なぜやるか）

社交ダンスのカウント練習アプリ。タイミングエンジン（整数tick・音声とメトロノームの同期・テスト約90件）は完成度が高いが、画面は開発者向けの寄せ集めで、
375px幅では再生ボタンが一覧に重なる・日英が混在して文字が切れる・設定が1画面に詰め込まれている、など「初見の人が使えない」状態。
これを **60〜70代の初見の人でも迷わず使え、海外でも通用するプロ品質のアプリ** に作り直し、まずPWAとして公開、反応を見てストア配信する。

## 合意済みの前提（ひとみうさの回答）

| 論点 | 決定 |
|---|---|
| アプリの形 | まずPWA（ホーム画面に追加・オフライン可）→ 後でApp Store / Google Play（Capacitor等で包む） |
| 初回公開の中身 | 10種目の**基本カウント**＋**自分で入れるルーティン**。公式・監修済みとは名乗らない |
| 目玉 | **先生が自分の声を録音 → 生徒に配る**。初期はファイル渡し（LINE・メール添付）、サーバー不要。リンク共有は後で |
| 表示言語 | 日本語＋英語（言語追加できる作りは維持） |
| 収益 | 無料公開。課金はストア版で検討 |
| 進め方 | 仕様は **Fable が中心**で固める → 完成まで **Opus（く！ちゃん）が采配**してサブエージェントで進める |

推測（Fable の裁定で確定させる）: 生徒の画面と先生の画面（録音・ルーティン作成）は入口を分ける／未監修の旧ルーティン24本は公開版から外し開発用に残す／運営はくうが株式会社名義。

## 再利用できるもの（調査結果）

- **そのまま移せる純粋モジュール**: `src/v2/` の `rhythm-parser` `rhythm-compiler` `dance-profiles` `timeline-view-model` `practice-range` `count-vocabularies` `localization` `routine-editor-state` `routine-draft` `figure-terminology` など
- **ブラウザ依存だが再利用可**: `audio-engine.js`（AudioContext注入式）、`voice-pack-loader.js`、`recording-normalizer.js`、`recorded-voice-pack.js`（base64埋め込みJSON書き出し・読み込み済み）、`recorded-voice-store.js`（IndexedDB）
- **作り直すもの**: `public/*.html` の画面（インラインに約1,600行の配線ロジック）
- **移すときの罠**: src/v2 内部の import に `?v=` が入っている（同じモジュールが二重読み込みになり得る）／fetch が全部 `cache:'no-store'`（PWAのキャッシュと衝突）／iOS の音声ロック解除処理がない／エラー文言・種目名・「（コピー）」が日本語固定／日本語の標準音声が無い

## 進め方（編成）

確立済みの定石（Japan Before Now で採用）に沿う: **Sonnet 資料まとめ → Fable 設計と裁定 → Opus 計画書 → サブエージェント実装 → 別エージェントでレビュー**。
Fable の文脈には長い資料を貼らず、ファイルで渡す。裁定は台帳に `Ruling N: 決定 — 理由 — 外れた時の代償` で残す。

### 段階1: 資料ブリーフ（Sonnet）
HANDOFF・AGENTS・globalization-architecture・前回UI設計書・上の再利用マップを1枚の `docs/app-v1/brief.md` に圧縮。作業ブランチ `agent/app-v1` を切る。

### 段階2: 設計と裁定（Fable）
Fable が以下を決め、`docs/app-v1/rulings.md`（台帳）と設計の骨子を書く。ひとみうさの判断が要るものは選択肢と根拠つきで質問として上げる。

- R1 技術構成（く！ちゃん推奨: Vite＋TypeScript＋軽量UIフレームワーク、エンジンは `src/engine` へ移設して既存テストを維持、Service Worker でオフライン、後でCapacitor）
- R2 画面構成と導線（生徒: 種目を選ぶ→再生、の最短2タップ／先生: 録音・ルーティン作成・配る）
- R3 ルーティン作成時のフィガー候補（未監修の旧データ由来のカウントを候補に出すか、出すなら「参考」扱いか、手入力のみか）
- R4 配布ファイルの形式（声＋ルーティンを1ファイルに束ねる／iPhone のPWAは「共有から開く」が使えないため、受け取り側の取り込み手順をどうするか）
- R5 日本語の標準音声（開発時にTTSで生成・onset実測。実行時のAPI依存は禁止のまま）
- R6 iPhone 特有の落とし穴（マナーモードでWeb Audioが鳴らない問題・画面スリープ・Bluetoothの遅れ）への対策と画面上の案内
- R7 高齢の方向けの基準（文字サイズ・タップ領域・コントラスト・1画面の選択肢数・言葉づかい）を数値で定義し、機械チェックに組み込む
- R8 法務（プライバシーポリシー・マイク利用の説明・先生の声を配る際の同意）
- R9 アプリ名（海外で通じる名前か）・公開先ドメイン → ひとみうさが決める

### 段階3: 見た目の方向決め（CLAUDE.md の順序どおり）
ワイヤーフレーム → **見た目2〜3案の比較HTML**（生徒の再生画面・先生の録音画面）→ ひとみうさが選ぶ。PC幅と375pxの両方で見せる。

### 段階4: 仕様書（Fable 監修・Opus 清書）
`docs/superpowers/specs/2026-10-xx-app-v1-design.md` に確定版を書いてコミット → **ひとみうさのレビュー**（ここが実装前の関門）。

### 段階5: 実装計画（Opus）
writing-plans で段ごとの計画書（テスト・完了条件つき）。想定する段:

1. 器づくり: 新アプリの骨組み、エンジン移設、既存テスト全件グリーン
2. 生徒の練習画面: 種目→基本カウント→再生（大きな再生ボタン・現在の拍の表示・速さ・繰り返し）
3. 自分のルーティン: 作る・並べ替え・保存（端末内）
4. 先生の録音: 12語の案内つき録音・自動頭出し（既存の正規化処理を再利用）・試聴
5. 配る・受け取る: 声＋ルーティンのファイル書き出し／取り込み
6. 日本語標準音声の生成と実測
7. PWA化: オフライン、ホーム画面追加の案内、iPhone の音声ロック解除・スリープ防止
8. 仕上げ: 日英の文言監修、法務ページ、アクセシビリティ、エラー時の画面

### 段階6: 実装（Opus 采配・サブエージェント）
superpowers:subagent-driven-development。コードが計画書に完備された段は Sonnet、エンジン移設や音声まわりなど危険な段は Opus。別パッケージは並列・同じアプリ内は逐次（worktree 運用）。各段ごとに別エージェントがレビュー → 最後に Opus 総合レビュー → 修正便1回 → 差分再レビュー1回。

## 確認方法（各段・最終）

- `npm test`（既存エンジンのテスト＋新規テストすべて成功）、`npm run timing:audit`（タイミングの数値が移設前と一致）
- Playwright で **PC幅と375px** の両方を開き、スクロール全域を撮って目視＋はみ出し・タップ領域・コントラストの機械チェック（`ui:check` を新アプリへ移植）
- 自動操作ブラウザは検収後に必ず閉じる
- **ひとみうさの iPhone 実機**で: マナーモード時の音・ロック解除後の復帰・Bluetooth・ホーム画面から起動・ファイルの受け取り
- 可能なら60〜70代の方に初見で触ってもらう（説明なしで「種目を選んで再生」できるか）
- 外部公開・push・デプロイは**ひとみうさの明示許可後**のみ
