## Ruling 1（R1）技術構成

**決定**: Vite ＋ TypeScript（UI層のみ）＋ Preact。エンジン（src/v2 の純粋モジュールとブラウザ依存モジュール）は **JS のまま `src/engine/` へ移設**し、`node --test test/engine/*.test.js` を維持する。TS 化はしない（`allowJs` で型だけ拾う）。PWA は `vite-plugin-pwa`（Workbox）。UI の自動テストは Playwright（既存 `tools/check-ui-accessibility.js` を移植）。後のストア配信は Capacitor。
補足の縛り:
- `?v=` キャッシュバスターは移設時に全て剥がす（Vite がハッシュ付与するため不要。現状 `audio-engine.js` → `voice-pack-loader.js?v=…` の内部 import が二重インスタンス化の元）。
- `cache:'no-store'` は `voice-pack-loader.js` から外し、fetch 実装を注入する既存の口（`fetchImpl`）で呼び出し側がキャッシュ方針を決める。
- 端末依存（AudioContext・MediaRecorder・IndexedDB・ファイル・共有・WakeLock）は `src/app/platform/` の薄いアダプタ越しにだけ触る。Capacitor で差し替える面をここに限定する。
- フレームワークの候補は Preact / Svelte / Lit。Preact を選ぶ理由は、サブエージェント（Sonnet/Opus）が React 流儀で最も誤りが少なく、バンドルが約4KB で、Capacitor WebView でも軽いから。

**理由**: エンジンは約89件のテストで守られた資産で、TS 化は価値よりリスクが大きい。UI は全面作り直しなので型とコンポーネント化の恩恵が最大。ビルド工程を入れるのは PWA（precache manifest・ハッシュ名）とストア包みのため。

**外れた時の代償**: Preact が合わなければ UI 層だけ捨てて Svelte 等に替えられる（エンジンとアダプタは温存）。Vite を入れたことで `python3 -m http.server` の手軽さは失うが、`npm run dev` 1コマンドで同等。

## Ruling 2（R2）画面構成と導線

**決定**: 下タブ3つ「練習・ルーティン・設定」。生徒の最短経路は **ホームの種目タイル → 再生ボタン＝2タップ**。2回目以降はホーム最上段に「前回: ワルツ ▶」カードを置き **1タップ**で再生開始。先生向け機能（声の録音・配る）は **設定タブ内の「声」**に入れ、ホームには出さない。「受け取る」は設定 →「声」→「ファイルから受け取る」の生徒操作（先生の案内文で誘導）。詳細は design-skeleton.md §1–2。
→ **D1・Ruling 16 で一部変更**: ホームに「先生の声で練習」カード（種目タイルの上）を置き、S7 へ直行できる。設定タブ内の入口も残す。

**理由**: 60〜70代の初見者は「最初の画面で何を押すか」が全て。種目名だけを大きく並べれば説明が要らない。先生機能を同じ画面に置くと選択肢が増え、初見者が迷う。

**外れた時の代償**: 先生が「録音機能が見つからない」と言う可能性。対策は設定タブに「先生の方へ」の見出しを立てること。ホームへ戻すのは1日の作業で済む。

## Ruling 3（R3）ルーティン作成時のフィガー候補

**決定**: **カウントの候補は出さない**。出すのは (a) その種目の検証済みテンプレート（`dance-profiles.templates`、例 ワルツ `123`・`12&3`）を「よく使うカウント」のボタンとして、(b) フィガー**名**の入力補助として `figure-terminology` の日英名（verified のもののみ。名前だけで、カウントは付けない）。未監修の旧ルーティン24本と 317 フィガーのカウントは公開ビルドに含めず、`tools/` と開発用ページに残す。

**理由**: HANDOFF の公開条件（内容レビュー済み・根拠あり）を満たさないカウントを初心者に見せる経路を作らない。名前だけなら誤った踊り方を教えることにならない。plan.md の「未監修の旧ルーティンは公開版から外す」推測はこれで確定。

**外れた時の代償**: 先生がルーティンを組む手間が増える（1フィガーあたり名前＋カウント入力）。後で監修済みカタログができたら、同じ入力補助の口に「候補」として差し込める（データ側の `reviewStatus` で出し分け）。

## Ruling 4（R4）配布ファイルの形式と受け渡し

**決定**:
- 形式: **1ファイル JSON**、拡張子は `.json`（iOS の LINE／Files が確実に扱うため独自拡張子にしない）。中身は `{schemaVersion:1, type:"dance-count-bundle", voicePack?, routines?[]}`。`voicePack` は既存 `exportRecordedVoicePack` の出力（base64 埋め込み、schemaVersion 1）をそのまま内包し、既存の単体パック JSON も**読み込みで受理**する（互換）。ファイル名は `声-<先生名>-<日付>.dancecount.json`（英 UI では `voice-<name>-<date>.dancecount.json`）。
- 先生の書き出し: `navigator.share({files})` が使える端末では共有シートに直接出す（LINE/メール/AirDrop を選べる）。使えなければダウンロード。
- 生徒の取り込み: **アプリ内「ファイルから受け取る」＝ファイル選択**が全プラットフォーム共通の正。Android Chrome の PWA は `share_target`（files）も登録し、LINE から「共有 → アプリ」で直接受け取れるようにする。iOS は共有ターゲット不可のため、「LINE で開く → 共有 → "ファイル"に保存 → アプリで受け取る」の4手順を**アプリ内に図解**し、先生の配布文（コピーできる定型文）にも手順を含める。
- 1ファイルの目安サイズ: 12語 × 約20〜40KB → 0.3〜0.6MB（LINE 添付は問題ない範囲）。上限は 20MB で受理を拒否する。

**理由**: 既にテスト済みの書き出し形式を核にすれば最小変更。サーバー無しの制約下で最も確実なのは「ファイル選択」。iOS の share-target 非対応は既知の壁なので、技術で埋めずに手順を製品に組み込む。

**外れた時の代償**: iOS 生徒の取り込み手順が4手順と長く、ここで脱落が出る。脱落が多ければ次版で「リンク共有（小さなサーバー）」を前倒しする（plan.md の「後で」）。

## Ruling 5（R5）日本語の標準音声

**決定**: 開発時に Google Cloud TTS（`ja-JP-Neural2-B` を第一候補、`-C/-D` を比較候補）で `count-vocabularies.js` の ja-JP 12語を生成し、既存 `tools/generate-google-voices.js` → `tools/measure-voice-onsets.js` で onset 実測、manifest schemaVersion 2 で `public/audio/default-ja-female-v1/` に同梱する。**採用ゲート**: 12語すべて (1) onset 実測済み、(2) ひとみうさが試聴して「数え言葉として自然」と判定、(3) `timing:audit` 相当の鳴り合わせ確認。1語でも不自然なら、その語だけ speakingRate／SSML（`<say-as>` や句読点）を調整して再生成。それでも駄目なら日本語標準音声は **人の録音（ひとみうさ）**に切り替える（録音パックの仕組みで同梱できる）。実行時 API 依存は禁止のまま。

**理由**: 英語で確立した手順の再利用が最短。短い単音（「に」「ご」）は TTS が不自然になりやすいので、聴感ゲートを明文化しておく。

**外れた時の代償**: TTS 不採用なら公開が録音の都合で数日ずれる。録音パックは既存形式で同梱できるため実装は増えない。

## Ruling 6（R6）iPhone の落とし穴への対策

**決定**（事実確認の記録 F1〜F5 参照）:
1. **マナーモード**: 起動時に `if ('audioSession' in navigator) navigator.audioSession.type = 'playback'` を設定（WebKit 関係者の案内。Apple 公式文書ではない＝実機確認必須）。さらに再生ボタンの**同じタップ内**で AudioContext を生成・`resume()`・無音バッファ再生（ロック解除）。`statechange` で `suspended` / `interrupted` を検知したら再生を止め、画面に「もう一度 ▶ を押してください」。
2. **鳴らない時の案内**: 再生開始から2秒以内に AudioContext が `running` にならない／`currentTime` が進まない場合、画面上部に「音が出ない時は: 横のスイッチ（マナーモード）を確認・音量を上げる・イヤホンの接続を確認」を出す。設定に常設の「音が鳴らない時」ページを置く。
3. **スリープ防止**: 再生開始のタップ内で `navigator.wakeLock.request('screen')`、`visibilitychange` で再取得。取得できない端末（iOS 18.3 以前のホーム画面アプリ等）では、再生画面に一度だけ「練習中は画面が暗くなることがあります。自動ロックを長めにすると便利です」を表示。音は AudioContext が生きている限り画面が暗くなっても続く前提にしない（確認項目に入れる）。
4. **Bluetooth 遅延**: 自動補正はしない。メトロノームと声は同じ音声クロックで鳴るので互いにずれない。画面のハイライトだけ `audioContext.outputLatency`（Safari 18.4 以降で取得可）を**表示側で**足す。取れなければ 0。手動調整は「くわしく」の奥に ±200ms のつまみを1つ（v1 では実装を後段に回してよい）。

**理由**: すべて「第二のタイミング計算を作らない」（AGENTS.md）を守る範囲で、画面側だけで吸収する。案内文は技術用語を避けた3行以内。

**外れた時の代償**: audioSession が効かない iOS 版では「マナーモードを切ってください」の案内で逃げる。WakeLock がない端末では画面が暗くなるが音は続く（続かなければ実機確認で発覚し、`<audio>` 要素の無音ループを併用する次善策に切り替える）。

## Ruling 7（R7）高齢の方向け基準（機械チェック可能な数値）

**決定**（全て新アプリの `ui:check` に組み込む。値は 375×667 と 1280×900 の両方で検査）:

| 項目 | 基準 | 機械判定 |
|---|---|---|
| 本文文字 | 18px 以上（`font-size`）。補助文 16px 以上。14px 未満は禁止（法務ページの注記も 14px 以上） | 可視テキスト要素の computed font-size |
| 主要ボタン | 高さ 56px 以上、再生／停止ボタンは 72px 以上・幅は画面幅の 60% 以上 | `.dc-primary` の rect |
| その他のタップ対象 | 48×48px 以上（旧基準 44 から引き上げ）、隣接タップ対象の間隔 8px 以上 | button/a/select/input/summary/label の rect と隣接距離 |
| 1画面の主要操作数 | 初期表示（スクロール無し）で押せる操作は **5個以下**（タブバー除く）。画面全体でも 9個以下。超える分は「くわしく」の折りたたみへ | 可視 interactive 要素の数 |
| 選択肢の数 | 1つの選択 UI の選択肢は 10 以下（種目10が上限根拠）。セレクトではなく大きなボタン群かリストで出す | `<select>` の option 数、`.dc-choice` の子数 |
| コントラスト | 文字 4.5:1 以上、24px 以上の太字は 3:1 以上、アイコン・枠線・無効状態も 3:1 以上 | 既存計算の拡張 |
| 色だけに頼らない | 状態は色＋形（アイコン・塗り）＋文字で示す | 手動レビュー項目（チェックリスト） |
| 動き | `prefers-reduced-motion` で装飾アニメ全停止。拍のハイライト以外に自動で動く要素なし。遷移は 300ms 以下 | CSS の `animation-duration`/`transition-duration` ≤ 300ms、reduced-motion 時 0 |
| 拡大 | `user-scalable=no` 禁止。200% 拡大で横スクロールが出ない | meta viewport の検査、ズーム時の `scrollWidth` |
| 行の長さ | 本文は全角 35 字（英 70 字）以内で折り返す。ボタン文言は最大 2 行、はみ出し禁止 | `scrollWidth > clientWidth` 検査（既存） |
| 言葉 | 下の言い換え規則。禁止語が UI 文言に出たらテスト失敗 | `ui-messages` の文字列を禁止語リストで走査 |
| 確認ダイアログ | 質問は1つ、ボタンは2つまで、取り消し側が左 | 手動レビュー項目 |

言い換え規則（日本語 / 英語）— 禁止 → 使う語:
- BPM → 「速さ」（数値は「♩=84」の形で小さく併記）/ "Speed"
- インポート／エクスポート／読み込み／書き出し → 「受け取る」「配る」「ファイルに保存」 / "Receive" "Share" "Save file"
- ルーティン → そのまま可（ダンサーの日常語）。「フィガー」も可
- メトロノーム → そのまま可。説明は「カチカチ音」
- カウントイン → 「はじめの合図」/ "Lead-in"（英は "Count-in" 可）
- 音声パック／ボイスパック → 「声」/ "Voice"
- 設定を保存／ストレージ／キャッシュ／同期／エラーコード → 使わない
- 「〜してください」で終わる依頼は1画面1つまで。エラー文は「何が起きたか」＋「次に押すもの」の2文構成

**理由**: 前回設計の 18px/44px/4.5:1 は維持しつつ、初見・高齢向けに「数」と「言葉」を機械で縛る。基準を数値にしておけばサブエージェントが勝手に詰め込めない。

**外れた時の代償**: 画面数が増え、慣れた人には1タップ余計になる。「くわしく」の中に逃がすので経路は壊れない。

## Ruling 8（R8）法務

**決定**:
- プライバシーポリシー（日英）を設定タブから到達できる静的ページとして同梱。内容の芯: 録音・ルーティンは端末内にのみ保存、運営者はデータを受け取らない、解析ツールなし（**v1 は解析を入れない**）、ファイルの受け渡しはユーザー自身が行う。
- マイク: OS の許可ダイアログの**前**に自前の説明画面（何を録るか・端末内にだけ保存・いつでも削除）を出し、「録音をはじめる」ボタンのタップで初めて `getUserMedia`。
- 声の配布: 「配る」操作時にチェック1つ「自分の声をこのファイルに入れて配ることに同意します。配り先は自分で管理します」。ファイルに `consent:{distributor:<先生名>, consentedAt}` を記録。受け取り側には「○○さんの声」と表示し、削除ボタンを声一覧に常設。
- 「公式・監修済みとは名乗らない」の表現を About に明記（団体名・級は出さない）。
- 運営者名義は **ひとみうさ判断**（下 Q4）。

**理由**: サーバーを持たない設計なので個人情報処理が最小で、地域別ポリシー（globalization-architecture）も v1 は日英共通で足りる。ストア版では Apple のプライバシー表示が要るため、今から「解析なし・外部送信なし」を事実にしておくと後が楽。

**外れた時の代償**: 解析なしなので利用状況が分からない。反応はストア前にユーザーの声で測る。

**決定**: 旧ルーティン・移行レビュー・音声比較の各ページ（`routine-migration-review.html` 等）は新アプリに**含めない**。旧 `public/` は `legacy/` へ移してそのまま動く状態で残し、`html-module-syntax.test.js` と `ui-assets.test.js` はパスを追従させて維持する。

## Ruling 11（追加）保存先と消失対策

**決定**: ルーティン・声・設定は **IndexedDB**（既存 DB `dance-count-v2` のバージョンを上げ、`routines`・`settings` ストアを追加。localStorage の下書き形式は読み取り互換のみ残す）。初回保存成功時に `navigator.storage.persist()` を要求。先生の録音完了時とルーティン保存時に「ファイルに保存（バックアップ）」を勧める1行を出す。
**理由**: iOS の未使用7日消去はホーム画面アプリでは緩和されるとされるが Apple の明文は見つからず（F5）。消えて困るのは先生の録音なので、ファイル保存を製品の動線に組み込む。
**代償**: 勧めが煩わしい。表示は各1回だけ。

## Ruling 12（追加）表示言語とカウント音声の言語

**決定**: UI 言語は端末言語から `resolveUiLocale` で決め、設定タブと初回ホーム右上の地球アイコンで切替。カウント**音声**の言語は UI と独立の設定（globalization 方針）。初期値は Q3 の回答で決める。
**代償**: 独立設定は設定項目が1つ増える。「声」画面の中に収める。

## Ruling 13（追加）練習画面の初期値と「くわしく」

**決定**: 初期値＝繰り返しオン・メトロノームオン・はじめの合図1小節・速さ「標準」（`practiceBpm`）。表に出す操作は「速さ3択（ゆっくり／標準／速め）・メトロノーム・はじめの合図・声」＋再生。「くわしく」の中に: 速さの細かい調整（スライダー 40〜220）・競技の速さ（`competitionBpm` 範囲）・繰り返しオフ・声のタイミング微調整。「ゆっくり」＝標準の 80%、「速め」＝標準と競技下限の中間（値は dance-profiles から算出、定数化）。
**理由**: Ruling 7 の「初期表示5操作以下」を満たしつつ、現行の機能を捨てない。
**代償**: スライダー派は1タップ増える。

## Ruling 14（追加）Android/PC の扱い

**決定**: 対応はするが設計の基準端末は iPhone（375px）。Android Chrome は `share_target` と `beforeinstallprompt` の案内を追加。PC は 1280px で同じ画面が崩れないこと（2カラム化はしない）。
**代償**: PC で余白が多い。v1 では許容。

## Ruling 15（追加）録音の形式

**決定**: 録音は現行どおり `MediaRecorder`（iOS は `audio/mp4`、Chrome は `audio/webm;codecs=opus`）→ `recording-normalizer` で WAV 化して保存・配布する（配布ファイル内は WAV、既存形式のまま）。再生側の decode 互換の心配をなくす。
**代償**: ファイルがやや大きい（Ruling 4 の見積もりは WAV 前提で約 0.5〜1MB）。LINE 添付に支障なし。

## 追加裁定（2026-10-11・D1〜D8 を受けて）

## Ruling 16（D8-(1)）「先生の声で練習」カードの置き場

**決定**: カードは **種目タイルの上**（「前回: ○○ ▶」カードの直下、初回起動なら見出しの直下）に、横幅いっぱい・高さ 56〜64px の1行（マイクのアイコン＋「先生の声で練習」＋右向き山形）で置く。タップ先は S7（声の一覧。録音・受け取るの2ボタンを含む）。種目タイルは1行 64〜72px に収め、**375×667（タブバー込み）の初期表示にカードと10種目すべてが入る**ことを `ui:check` の判定に加える（カードの rect と各タイルの rect が最初のビューポート内）。D1 の「種目タイルの下」は、この位置では1画面目に入らないため上に改める（PO 方針「前に出す」を優先）。
**理由**: 目玉を「見える位置」に置きつつ、生徒の最短経路（タイル→▶）を1行ぶん下げるだけで済む。種目を選ぶ見出しは残るので初見者の迷いは増えない。
**外れた時の代償**: 生徒が毎回「先生の声」を目にして押してしまう可能性。S7 は「戻る」で即戻れ、何も壊れない。

## Ruling 17（D8-(2)）「戻る」と下タブの出し分け

**決定**: 画面を2種に分ける。
- ルート画面（S1・S3・S6）と一覧画面（S7・S12・S13）: 下タブを表示。「戻る」は一覧画面のみ左上に表示。
- 集中画面（S2・S5・S4・S8・S9・S10・S11）: 下タブを**隠し**、左上に必ず「‹ 戻る」（48px 以上、山形＋文字ラベル、アイコン単独禁止）。下固定の主ボタン（▶／全体を試聴／録音する／ファイルを作る）はタブバーと同居させない。
- 「戻る」は再生中なら音を止めて戻る（確認なし）。S8 は録音済みの語を保存した上で戻る（確認なし、再開可）。
- ブラウザ／端末の戻る操作は同じ動きにする（ハッシュ履歴に画面ごとに1件積む）。
**理由**: 60〜70代の初見者にとって「戻れない」は最大の不安。集中画面で下タブを隠すのは、下に ▶ とタブが並ぶと誤タップが増えるため。
**外れた時の代償**: 集中画面からタブ直行ができず1タップ増える。許容。

## Ruling 18（D8-(3)）「1画面の主要操作数」の数え方（機械判定）

**決定**: 375×667・スクロール無しの初期ビューポートで、次を数える。
- 対象: 可視の `button, a, [role=button], input, select, summary, label[for]`。rect が初期ビューポート内に**完全に**入るもの。
- 除外: `[data-nav]`（下タブ）、`[data-back]`（戻る）、`[data-utility]`（言語切替など右上の補助）。
- まとめ: 同じ `[data-group]` 祖先を持つ要素は **1操作**として数える（速さ3択＝1、種目タイル10個＝1、カウントの型チップ群＝1）。`[data-group]` の中の選択肢は 10 個以下（Ruling 7 と同じ）。
- `summary[data-more]`（「くわしく」）は主要操作に数えないが、1画面に 1 個まで。
- 上限: **初期表示 5 以下**、画面全体（スクロール含む）9 以下。
- 当てはめ: S1＝前回カード(1)＋先生の声(1)＋種目タイル群(1)＝3。S2＝速さ(1)＋メトロノーム(1)＋はじめの合図(1)＋声チップ(1)＋▶(1)＝5。したがって **カウントの型チップ（ワルツ `1 2 3`/`1 2 & 3` 等）は「くわしく」の中へ**、初期値は `templates[0]`。選んだ型は種目ごとに記憶する。
**理由**: 「要素数」でなく「判断の数」を数えれば、グループ化で画面を整理する動機になる。属性で宣言させればサブエージェントの実装も検査も機械的。
**外れた時の代償**: ワルツの `12&3` 派が1タップ余計。種目ごとに記憶するので2回目以降は影響なし。

## Ruling 19（D8-(4)）S2 のトグルは Ruling 13 のまま

**決定**: 表に出すトグルは **メトロノーム・はじめの合図** の2つ。繰り返しは初期オンで「くわしく」の中。比較 HTML（b-studio-navy.html）の「繰り返す」は清書時に「はじめの合図」へ差し替える（モックの作り直しは不要）。
**理由**: はじめの合図は「▶ を押した直後に何が起こるか」を変えるので、初見者が最初に調整したくなる設定。繰り返しはほぼ常にオンで、変えるのは慣れた人。
**外れた時の代償**: 繰り返しを切りたい人が「くわしく」を開く1タップ。

## Ruling 20（D7）曲を載せる口 — v1 の最小インターフェース

**決定**: v1 では **テンポ写像（TempoMap）の抽象化だけ**を作り、曲の音・画面・同梱・計測ツールは作らない。
- 作るもの（v1）:
  1. `src/engine/tempo-map.js`（純粋モジュール）: `tickToMs(tick)` / `msToTick(ms)` を持つ2実装。`constantTempo(bpm)`（現在の `tick × 60000 / (bpm × 960)` と同値）と `beatMapTempo(beatsMs[], beatsPerBar)`（拍ごとの実測時刻の間を区分線形補間。範囲外は最後の拍間隔で外挿）。単体テストで (a) constant が現行計算と全 tick で一致、(b) beatMap が拍時刻をちょうど返す、(c) 単調増加、を固定。
  2. `audio-engine.js` と `timeline-view-model.js` の「tick → 秒」をこの1箇所に集約（constant を既定で注入）。**第2の時間計算は作らない**: メトロノーム・声・ハイライトは引き続き同じ tick 列から、同じ TempoMap で秒に変換する。移設後の `timing:audit` の diff ゼロが完了条件（constant 経路は数値が変わらないこと）。
  3. データの型だけ定義（実データなし）: `TrackProfile { id, danceId, title, file, durationMs, beatsPerBar, tempo: {kind:'constant', bpm, firstBeatMs} | {kind:'beatMap', beatsMs:number[]}, license:{kind:'CC0'|'PD-recording'|'CC-BY', source, url, note}, measuredAt }`。練習セッション状態に `track: null` の席を予約。
- 作らないもの（第2弾）: 曲の音の再生（AudioBufferSource を tick 0 ＝ `firstBeatMs` に合わせて開始する処理）、曲の選択 UI（S2 の「くわしく」に「曲に合わせる」として入れる予定）、曲の同梱とライセンス台帳、拍位置の計測ツール（`tools/measure-track-beats.js`）、ユーザー自身の曲の読み込み（範囲外、D7）。
- 第2弾での前提を今決めておく: 曲ありのときは速さ3択を無効（タイムストレッチはしない。曲の実測テンポで鳴らす）、カウントインは曲の先頭無音部の長さで代替、ルーティンは曲より長ければ曲の末尾で停止。
**理由**: 今の「tick→秒」を抽象化しておけば、第2弾は「TempoMap を曲のものに差し替えて音源を同時に始める」だけで済み、エンジンの構造を再度いじらない。v1 の公開は遅れない（純粋モジュール1本＋テスト）。
**外れた時の代償**: 生演奏のテンポ揺れが拍の区分線形で足りない場合（ルバートが極端な曲）は曲の選定で避ける。抽象化が不要になっても constant 実装がそのまま残るだけで害はない。

### Ruling 20 訂正メモ（2026-10-11・段1実装時）
- tick→秒の集約対象は `audio-engine.js`・`rhythm-compiler.js`・`dance-timing-audit.js`。`timeline-view-model.js` に該当計算はない。
- beatMap の外挿は、最初の拍より前は最初の拍間隔、最後の拍より後は最後の拍間隔。
- 関連（Ruling 21）: 1024px 以上の上部タブは段2で実装する（段1は下タブのみ）。

## Ruling 21（§16-1）PC 幅のレイアウトとタブの位置

**理由**: PO が選んだモックの PC 図（S2 2カラム・上部ナビ）を「同じ部品の並べ替え」として受け入れれば、Ruling 14 の目的（PC 専用の作り込みで工数を増やさない）と矛盾しない。

## Ruling 22（§16-2）拍子の副題はやめ、「最初に鳴るカウント」を副題にする

**決定**: 種目タイル（S1）と再生画面の見出し（S2/S5）の副題は「N拍子」ではなく、**その種目の `templates[0]` を表示用に整形したカウント**にする（例: ワルツ「1 2 3」、タンゴ「S S Q Q S」、スローフォックス「S Q Q」、サンバ「1 a 2」、パソドブレ「1 2 3 4」、ジャイブ「1 2 3 a 4 5 a 6」）。整形は現在カウント表示と同じ関数（声キー→表示語、`&`→「&」、`a`→「a」、日英共通）。拍子（2/4・3/4・4/4）は**どこにも表示しない**。エンジンの `beatsPerBar`（パソドブレ 4・サンバ 2）はそのまま。
**根拠の確度**: パソドブレの音楽が 2/4 で書かれることは一般的な複数資料で確認（MasterClass・Library of Dance 等。WDSF 等の規程では未確認）。エンジンがパソドブレを「1小節4拍」で数えるのは既存設計（テンプレート `1234`・`12345678`）で、ダンス上の慣習としての正しさは**本件では検証していない**。だからこそ拍子を名乗らず、「何が鳴るか」だけを見せる。
**理由**: 初見者に有用なのは「3拍子」より「1 2 3 と鳴る」こと。音楽理論の主張を UI から消せば、未検証知識を表示しない原則（AGENTS.md）にも沿う。
**外れた時の代償**: 「拍子を知りたい」人には情報が無い。要望が出たら S13 か「くわしく」に出典付きで追加する。副題が長いジャイブ（15字）は 16px でタイル幅 170px に収まる（U10 で検査）。

## Ruling 23（§16-3）警告バナー表示中の ui:check

**決定**: S2/S5 は **通常状態とバナー表示状態の両方**を検査する（テスト用クエリ `?ui-state=no-sound` でバナーを強制表示）。バナー内の操作は1つだけ（「音が出ない時は ›」リンク、`[data-alert-action]`）で、**U4 の主要操作数からは除外**し、U1・U3・U7（文字・タップ・コントラスト）は適用する。バナー状態でも `[data-group="speed"]` と `[data-play]` が 375×667 の初期ビューポートに完全に入ること（バナーの高さは 375 幅で 120px 以下）。声チップやトグルがフォールド下へ押し出されるのは許容。
**理由**: バナーは一時的で、出ている間に生徒が触るのは「もう一度 ▶」と速さだけ。例外ではなく「もう1つの状態」として検査すれば、バナーで画面が壊れる事故を機械で防げる。
**外れた時の代償**: バナー文を長くできない（3行以内）。S11 に詳しい説明を置くので足りる。

## Ruling 24（§16-6）速さ3択の定義（ワルツ問題）

**決定**: 「ゆっくり」＝`round(practiceBpm × 0.8)`、「標準」＝`practiceBpm`、「速め」＝`min(round(practiceBpm × 1.1), competitionBpm.max)`。定数 `SPEED_SLOW_RATIO=0.8`・`SPEED_FAST_RATIO=1.1` を1か所で持つ。ワルツ: 67 / 84 / 90。他の種目は全て「速め」が標準より大きく、競技範囲の上限を超えない（例: タンゴ 123、クイックステップ 176、ジャイブ 150）。本当の競技テンポは「くわしく」の「競技の速さ」ボタン（`competitionBpm.min`）で出す。
**理由**: 「速め」は初見者にとって「少しだけ速い」であるべきで、競技テンポとの中間という定義は種目によって跳びが大きすぎた（ルンバ 80→90 は良いがクイックステップ 160→176 と同じ式でワルツが 84→84 になる）。比率なら全種目で意味が揃う。比率 0.8/1.1 は製品判断で、ダンス上の根拠はない。
**外れた時の代償**: 「速め」が競技テンポに届かない種目が多い。競技の速さは「くわしく」にあるので経路は残る。単体テストで10種目の3値が「ゆっくり < 標準 < 速め ≤ 競技上限」を満たすことを固定する。

## Ruling 25（§16-7）先生が録音する言語と選ぶ場所

## Ruling 29（Q5）Bluetooth の表示遅延はエンジンの `frame()` に表示用の遅れを渡す（計画者の推奨を却下）

**決定**: UI 側の setTimeout 遅延キューは**採用しない**。代わりに `PracticeAudioEngine` のコンストラクタオプションに `displayLatencySeconds: () => number`（既定 `() => 0`）を足し、`frame()` の経過時間だけを `elapsed = this.audioContext.currentTime - this.displayLatencySeconds() - startTime` にする。予約（`scheduleAhead`・`scheduleClick`・`start()` の戻り値）は一切触らない。
- 呼び出し側: `platform/audio-context.ts` が `() => clamp(context.outputLatency ?? 0, 0, 0.5)` を渡す（取れない・NaN・負・0.5秒超は 0）。毎フレーム読むので Bluetooth の接続・切断に追従する。
- テスト: `test/engine/audio-engine.test.js` に「latency 0.2 のとき currentTime=T の frame は、latency 0 の currentTime=T−0.2 と同じ `originalTick`・`countIn` を返す」を追加。`npm run timing:compare` と予約時刻のゴールデンは**変化ゼロ**が条件（既定 0 なので既存テストも不変）。
- 手動つまみ（±200ms）は v1 では入れない（同意）。

**理由**: 「表示だけ遅らせる」は仕様 §9「表示は currentTime（＋outputLatency）から tick を読む」そのもので、その計算は `frame()` にある。setTimeout の列は壁時計で動く第2の時計で、AGENTS.md「第2の時間計算を作らない」に反し、停止時の掃除・順序・ジッタの面倒も増える。エンジンの変更は `frame()` の1行＋オプション1つで、onFrame の出力契約は変わらない。

**外れた時の代償**: `src/engine` に手を入れる例外が1つ増える（仕様 §10）。範囲は `frame()` のみと明記し、レビューで予約経路に触れていないことを diff で確認する。
