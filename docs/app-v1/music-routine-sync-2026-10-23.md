# 音楽とルーティンの同期実験 — 2026-10-23

ひちゃんの「シンプルなカウントだけでなく、ルーティンでも合うか確認」に対応。解析済みの拍地図は変更せず、既存のルーティンcompilerを接続した。

## 試す

開発サーバー `http://127.0.0.1:5195`。ワルツの例:

`http://127.0.0.1:5195/__music/review?track=waltz-33445d26a14c&program=sample-waltz`

「ルーティン・速さなどを選ぶ」内で、基本カウント／実験例／同じlocalhostのアプリに保存したルーティンを選択できる。種目が一致するもののみ表示。保存済みの内容は読み取るだけで、書換え・複製・移行はしない。通常の「使う」の音楽画面へルーティン選択を追加した段階ではなく、制作側の検証画面での実験。

## 時間の扱い

- `compileMusicProgram`をセッション・確認画面・WAV書き出しで共有。既存`compileRoutine`の960ticks/beat、フィガー長、半拍、休符を保持し、全体のticksを一度だけ移動する。フィガーごとに1へ戻さない。
- 数字の最初の語と相対位置から小節内の開始位置を合わせる。ルンバ／チャチャの「2」は小節の2拍目。途中のフィガー範囲も元の番号・小節位相を維持。
- 曲が先の2小節は、ルーティン開始を後ろへ移動する。先頭フィガーを音量ゼロで消費する方式にしない。
- 声が先の2小節は基本カウントによる準備。ルーティンのフィガーを先へ消費せず、音楽開始後に最初のフィガーから始める。
- 既存`tempo-map`で、推定された不均等な拍間隔へ変換する。一定BPMへの固定、拍地図の再解析はしない。
- 選択したルーティン全体が6小節の安全区間に入らない場合は停止し、最初／最後のフィガーを選ぶ案内。自動切捨て・音楽の延長・長さを無理に合わせる変形はしない。
- 最後のフィガーが終わったら表示を消し、曲は区間末尾まで鳴らす。半拍の`&`も同じ時刻変換。`@`は発声ジョブを作らない。

## 実験用の内容

- ワルツ: 監修済み表からウィスク123、シャッセ・フロムPP 12&3、ヘジテーション・チェンジ123123。計4小節。半拍と2小節フィガーの切替を確認する組合せで、踊りの接続順の認定ではない。
- ルンバ: 2341 → 2&341 → 2341。
- チャチャ: 234&1 → 23&41 → 234&1。
- 後二者は時間配置の技術実験。実際のフィガー名に未監修のカウントを付けて配布しない。例はメモリー内のみで利用者DBへ追加しない。

## 再現

```
npm run typecheck
npm test
npm run timing:compare
npm run smoke:music:routines
/tmp/dc-music-analysis-venv/bin/python tools/music-probe/verify-exports.py output/music-probe/routine-browser-evidence.json
```

`smoke:music:routines`は隔離Chrome contextで5曲の実再生、全3種目×3速度の実WAV保存、保存ルーティンの読取とフィガー範囲、設定変更時の書出し中止、画面幅、WCAGを確認。証拠は`output/music-probe/routine-browser-evidence.json`と`routine-export-verification.json`。波形照合は推定拍への音声配置を検証するもので、音楽の推定正解や踊りの構成監修とは区別する。

## この先

正式な「使う」へのルーティン選択は未接続。長いルーティン向けの監修済み区間長、フィガー範囲と繰り返しの操作を、初心者の画面を増やしすぎない形で決める。曲ごとの拍の聴取確認・実機確認・販売の権利条件は従来の受入と同じ。公開・課金・音源のGitHub送信はしていない。

## 検証結果と監査の修正

- 自動テスト730 PASS、型検査PASS、既存timing golden差なし。公開build1079ファイルPASS。
- 提供5曲の実Chrome再生で全3フィガーへ遷移。ワルツの2小節フィガーは6語を保ち、全種目の半拍を確認。曲先／声先／同時と3速度を組合せて検査。
- 3種目×3速度の実保存9WAV、153語を標準声の波形と照合。予定時刻への最大配置差約0.0114ms（48kHzの1sample未満）、最小相関0.818以上。拍の推定自体を再認定する値ではない。
