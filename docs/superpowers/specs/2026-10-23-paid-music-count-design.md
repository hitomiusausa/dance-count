## 1. 今回の目的と決定の境界

ひちゃんの「有料で音楽＋カウント同期再生をつけたい」という依頼を第2弾の出発点とする。初心者が、種目に合う曲を選んで押すだけで、音楽・カウント音声・拍表示を一緒に使えることを目指す。

- 今回承認されている作業: `Paper Umbrella.wav` をルンバ候補として端末内で試すこと、調査、設計。続いてひちゃんが**設計図の作成とコーディング開始、および「使う」セクションへの統合**を許可（2026-10-23）。実装設計図は[音楽練習の実装計画](../plans/2026-10-23-music-practice-implementation.md)。
- この文書の提案: 現在のカウント練習は無料の入口として保ち、**審査済み楽曲との同期練習**を有料機能にする。既存の録音・共有・編集まで一括で有料化する提案ではない。
- 未決: 買い切り／定期購読／曲パック、価格、無料試聴、販売地域、オフライン利用期間、決済事業者、認証方式、対象端末、発売時に審査を終えて収録する曲数。
- 未承認: 公開・配信・契約・課金設定・決済実行・ストア申請・音源の外部送信。
- `docs/app-v1/HANDOVER.md` §2「日英・無料」はv1の既存決定として残す。本提案を承認した時に、第2弾の差分として決定台帳へ記録する。過去の決定を無断で書き換えない。

最初の技術検証は「1種目・1曲・おすすめの短い練習区間・元の速さ」から段階的に通す。商品として準備する目標と追加希望は§1.1のとおり。Paper Umbrellaを採用する場合は、**審査済みbeatMap対応を初回から必須**とする。全曲再生・音程維持の速度変更・書き出しは、対応する検証を通った段階で提供する。元速度だけで販売開始するとは決定していない。未対応操作を押せる状態にはしない。

## 3. Paper Umbrella の試作と採用判定

対象原本: `/Users/usausagi/Downloads/Paper Umbrella.wav`。元ファイルは上書きしない。試作は本番`src`とは別のローカル専用labで行い、既存compiler・tempo-map・voice-loaderを再利用する。

うさこの実測（2026-10-23）: 長さ329.96秒、48kHz・stereo・PCM16、音声データ約63.4MB（約60.4MiB）。48kHz float32 stereoとして全曲をdecodeすると約126.7MB（約120.8MiB）となり、圧縮データ・一時コピー・声・ブラウザ本体は別に必要。音源サイズだけで端末負荷を判断しない。

原本SHA-256: `387307378d92a62759301c59fd22800f8ef0571543b2229132f6f28d16e86e83`。解析は`output/music-probe/analysis.json`（非公開・Git対象外）に方式・versionとともに保存。librosa spectral-flux＋DP trackerで689拍候補、全体の一定gridへのfitは131.19395 BPM。30秒窓では前半約135.27→後半約125.21 BPMのfitとなった。**検出拍gridと全体一定gridの残差**は絶対値中央値約702ms、95%点約1,738ms、最大約2,659ms。これは実際のテンポ変動・追跡誤り・拍抜けを分離した測定ではない。音楽そのものの確定ドリフトや人手ground truthとは呼ばない。

前半20〜50秒のonset自己相関では約133.64 BPM（半分約66.82、別候補約91.12等）も得られ、131前後の候補を別方式が支持した。プロジェクトのルンバ目安100〜108 BPMより速いが、この数値だけで種目を認定しない。半倍／倍速、音楽の拍子、小節1拍目とダンス適性は未監修。

ローカル比較labは`tools/music-probe/`、起動時URLは`http://127.0.0.1:5194/`。原本をGitやpublicへ置かず、serverが前半20秒・中盤140秒・後半280秒付近の32秒だけを切り出す。compilerの`2341`を曲の2拍目から配置する候補で、固定BPMと推定拍時刻を比較する。**この位相は試作仮説であり、監修済み小節頭ではない。**

ひちゃんの実聴評価（2026-10-23）: 「一定のBPMに合わせるカウントはズレてると思ったけど、推定時刻の方は合ってたと思う」。この比較は拍地図方式を採る根拠になる。Paper Umbrellaでは固定BPMを比較用にとどめ、製品経路は審査済み拍地図を使う。全曲・全位相の専門家監修、ルンバ採用、権利承認を意味しない。

同日の技術検証（うさこからの報告）:

- Chromeで3区間の再生・表示・停止を確認。既存698テストと、変動tempo・非ゼロ範囲頭・位相・offset・境界の試作3テストが通過。
- 最終検算ではChromeの44.1kHz読込経路からOfflineAudioContextで3区間を出力し、計207語（71/70/66）の語別チャンネルを再測定。既存`measureOnset`の**5ms測定窓**で発声onsetと予約targetの差がすべて0ms。サンプル精度の0誤差や、実際の音楽の拍との一致を示す値ではない。
- 最終mixのpeakは前半0.666・中盤0.650・後半0.651でクリッピングなし。予備48kHz後半検算の0.653とは経路を区別する。初期のmono測定が前語の余韻を誤検出した訂正と、最終証拠は[着手メモ](../../app-v1/music-probe-2026-10-23.md)に記録。全曲や全音声の音質保証ではない。
- 検出拍のcoverageは0.129705〜315.921995秒。**末尾約14.038秒は拍未検出**。全曲モードでは音楽だけを鳴らすか追加審査し、拍地図の外挿でカウントを続けない。最終拍は区間終端を作るための次拍境界が未確認なので、その直後の1拍も自動承認しない。

採用手順:

1. 原本hash、長さ、サンプルレート、チャンネル、ピーク、無音部を測る。原本と加工版を別ID・別hashで結ぶ。
2. 機械解析でBPM候補、半倍／倍速候補、拍候補、変動・低信頼区間を出す。生成時のプロンプトや曲名を拍の根拠にしない。
3. 拍と小節頭を人が聴いて確認する。特にルンバでは「音楽の1拍目」と「最初に発声・移動するカウント」を別々に確認する。実装の既存カウント表記を推測で変更しない。
4. 冒頭・中盤・終盤とフレーズ境界を確認し、曲ごとに一定テンポで通すか、拍地図が必要かを決める。Paper Umbrellaは今回の比較結果から拍地図を採る方針。短い区間の成功だけで全曲を承認しない。
5. 初心者が入りやすい完全小節の8〜16小節程度を候補にし、始点・終点とループ接続を聴く。小節数は製品案であり、ダンス規則ではない。
6. 音楽審査と権利審査が両方完了した版だけを販売カタログへ進める。

## 4. 初心者の操作と有料機能の境界

**「使う」内を正式な入口にする。** Home（`#/use`）の「音楽と練習」から曲一覧→曲の練習画面へ進む。既存の種目タイル・フィガー練習・ルーティンの導線は保ち、初段では下タブを増やさない。曲一覧は種目で絞り、1曲を選ぶとおすすめ区間・元の速さ・既存の選択済み音声を用意する。曲選択後は大きな「▶ はじめる」で鳴る。将来、種目の練習画面にも同種目の曲一覧への補助リンクを足せる。

実装第一段はこの正式導線へ接続した**ローカル開発モード**。未審査のPaper Umbrellaと拍解析データは開発専用providerからのみ読み、公開ビルドの曲一覧・bundle・precacheには含めない。商品全体が完成・購入可能になったという表示はしない。

通常画面には曲名、速さ、再生／停止、繰り返し、カウント表示を置く。「くわしく」に音楽／声の音量、メトロノーム、声のタイミング、練習区間、対応済みの速度変更を置く。BPM測定・拍地図編集・権利項目は制作側の道具に置く。

| 状態 | 表示と操作 |
|---|---|
| 未購入 | 曲名と「音楽と練習するには購入が必要です」。価格・期間・対象曲が確定するまでは購入画面を実装しない。無料試聴を設けるなら独立した許諾済み短い素材を配信する |
| 利用権あり・未保存 | 「この端末に準備する」→容量と進行状況→「はじめる」。初回は通信が必要と開始前に伝える |
| 準備中 | 中止できる。前の選択が後から鳴らないよう世代番号とAbortで無効化 |
| オフラインで利用可 | 「電波がなくても練習できます」。有効期限のある商品なら利用期限を併記 |
| 利用確認が必要 | 「ネットにつないで購入を確認してください」＋「カウントだけで練習する」 |
| 再取得が必要 | 「曲をもう一度準備してください」。購入をやり直す誘導にはしない |
| 読込・decode失敗 | 曲は鳴らさず理由と再試行を示す。音楽なしへの切替はユーザーが選ぶ |

設定に「購入を確認する」「この端末の曲」「曲の出典」を追加する。音楽の利用権と録音音声／ルーティンの所有データを分け、解約・ログアウトで後者を消さない。音楽・購入情報・署名URL・利用権tokenは既存の先生／生徒向け共有ファイルに入れない。

日英UI、既存タッチサイズ・文字・コントラスト・主要操作数の基準を適用。拍は色だけで示さず、現在の数字／語を併記する。認証・購入画面もスマートフォンで戻れることを受入条件にする。

## 5. 曲・拍・カウントの唯一の基準

### 5.1 データの座標

- 1拍は既存どおり960整数tick。イベント・小節・区間境界・ループ境界・ルーティンの接続位置を整数tickで保持する。
- `trackTick=0` は**制作側が確認した基準小節の1拍目**。ファイル先頭と一致するとは限らない。弱起／イントロは負tick側またはカウント対象外として明示する。
- `T(trackTick)` は元の曲ファイル先頭からの秒数。一定テンポ＋先頭offset、または実測拍地図から`tempo-map.js`内だけで求める。BPMと秒の独自換算を画面・音楽loaderに作らない。
- 既存`constantTempo(bpm)`はそのまま残す。曲用のoffset付きmapを新設し、`firstBeatMs`を本当に反映する。既存`beatMapTempo`の`beatsMs[0]`も基準小節1拍目として入力を正規化する。
- 拍位置の逆写像は連続値を返してよい。ハイライトはその値と整数イベント境界を比較する。描画フレームごとにtickを丸めて積算しない。
- ルーティンのtickは曲tickへ整数offsetで配置する。小節位相が合う配置だけを自動提案する。任意のフィガー先頭を曲の1拍目へ丸めない。
- ルンバの試作`2341`では、コンパイル済み最初の「2」を音楽の2拍目に置く候補と、曲mapの基準1拍目を区別する。発声を合わせるために曲全体の1拍目定義を1拍ずらさない。最終の対応は監修したtemplate anchorとして保存する。

### 5.2 区間と反復の再生計画

承認済み曲区間を半開区間`[s, e)`、固定の速度倍率を`r > 0`、開始AudioContext時刻を`a`とする。変換関数とその逆写像はtempo-map側の共通transport変換に集約する。

```text
区間の実時間 D = (T(e) - T(s)) / r
区間内tick qの第n周の発音時刻 = a + n * D + (T(q) - T(s)) / r
現在位置 q = T⁻¹(T(s) + r * (経過秒 - n * D))
```

拍地図で`T(e - s)`や`T(q - s + n * (e - s))`を呼ばない。2周目は曲の後半へ進まず、同じ区間を同じ拍地図で再生する。累積加算で次周時刻を求めず、`a + n * D`から導く。終端`e`のイベントを次周先頭と二重発音しない。

音楽は同じAudioContext内のBufferSourceから鳴らし、開始時刻`a+nD`・元音源offset`T(s)`・区間の元音源長`T(e)-T(s)`を使う。分割配信ではchunk原点の秒だけ引いてbuffer内offsetへ変える。声とclickも同じ変換結果で予約する。別のHTMLAudioElementの再生位置を第2の時計にしない。

`start(when, offset, duration)`のoffsetとdurationは元bufferの秒であり、倍率適用後の秒ではない。stop時刻はAudioContextの秒で指定する。APIの単位を型・名前・テストで区別する。Web Audioのplayheadと予約時刻の定義を参照する。[W3C Web Audio](https://www.w3.org/TR/webaudio/#AudioBufferSourceNode)

予約は先読み窓内の音楽chunk・声・clickだけに限定し、長い曲の全イベント／全nodeを一度に作らない。遅延で窓を取り逃したら大量の過去イベントを即時発音せず、全音を止めて再開を案内する。

### 5.3 カウントのパターンと曲の終わり

「基本カウント」は既存compilerの整数イベントを、曲の承認済みカウント区間まで整数tickで繰り返し配置する。数拍のパターン終了で音楽全体を巻き戻さない。

ルーティンは全体をcompileしてから指定範囲を取る現行方式を継続する。ルーティンを曲に合わせて繰り返す場合、区切りの小節位相が合わないものは自動反復しない。短いルーティンを全曲で反復する機能は、接続規則の監修後に追加する。

| 操作 | 音とカウントの仕様 |
|---|---|
| おすすめ区間を1回 | `[s,e)`だけ再生。声・clickは`e`以降へ出さず、短いフェードで終了 |
| おすすめ区間を繰り返す | 音楽とカウントが一緒に`s`へ戻る。ループ対応と審査された完全小節区間だけ許可 |
| フィガー／範囲 | 元ルーティンの位相を保持して曲内の承認済み範囲へ配置。必要tick数が足りなければ開始不可。途中小節範囲は単発のみとし、ループを推測で許可しない |
| 先頭へ | モードの先頭へ停止して戻る。音楽練習なら`s`、全曲ならファイル0秒。カウントインも最初から |
| 全曲（後段） | 音源0秒から終端まで。イントロ／アウトロ・拍不明区間は音楽のみ、明示した承認区間でだけ数える。初版の全曲モードは単発、人工カウントインなし。表示も「曲をはじめから聴く」として練習区間と区別 |
| 停止・中断・画面離脱 | 音楽・声・click・予約を全停止。電話・ロック後の自動再開なし。最初は一時停止／任意seekを持たず、再開は選択区間の頭から |
| 自然終端 | 残ったnodeを解放し、Session/WakeLockも停止状態に。ファイル長と曲地図の差を勝手な外挿カウントで埋めない |

カウント可能範囲は検証済みのmap coverage内に限定する。beatMapの端外挿は合図生成など許した用途だけに使い、未測定の曲後半を正確な拍として扱わない。曲区間を跨ぐ拍子変更は初版対象外。

### 5.4 はじめの合図・声・音量・速度

- おすすめ区間の合図は既存設定を引き継ぎ、基本練習はオンなら2小節。ルーティンの1／2小節も維持する。合図は曲開始前のclickのみ。ループ2周目以降には挟まない。
- 合図用は選択始点の承認済み直前拍間隔、存在しなければ最初の承認済み拍間隔から一定の導入mapを作り、元小節位相を保持する。map生成と時刻変換はtempo-mapへ集約。合図の直後に`s`が来る。負の音源offsetを要求しない。
- voiceは標準／録音の選択を継承し、`onsetMs`、全語・個別語offsetを既存loaderで適用する。**音楽速度を変えても声の音程と語の再生速度は変えない**。目標発声時刻だけが変わるので、onset補正やユーザーms補正を倍率で割らない。
- 次語・ループ境界・区間終端で声がはみ出さないようfade停止。先頭語のonset補正分を含めた予約余裕を確保する。短い語間の重なりは既存の頭を守る方針を継承する。
- 音楽・声・clickを別gain busへ接続する。無料の既定経路は既存destinationと音量のまま。初期音量は実音の聴感で決め、混合ピーク・クリッピングを測る。常時の自動duckingは初版に入れない。
- 初回試作は`r=1`。音楽モードに既存の種目BPM設定をそのまま流用しない。曲の元速度が基準で、可変テンポ曲には単一の「正確なBPM」を表示しない。
- 次段で試す速度候補は0.8／1.0／1.1倍。これは製品案。単純なBufferSourceのplaybackRate変更では曲の音程も変わるため、その方式で販売するか、音程維持の処理済み速度別素材にするかを聴感評価後に決める。
- 速度別素材を用意する場合は各素材の遅延・長さ・拍位置を再測定し、元曲版・加工版・拍地図版を結ぶ。実行時time stretch／AudioWorkletは後段の別検証とし、二重時計を持たせない。
- 再生中の速度変更は全停止→選択区間の頭から合図付き再開。瞬時の連続速度変更、スクラブ、速度rampは初版対象外。旧予約はgenerationで無効化する。

### 5.5 書き出し（追加希望・設計候補）

書き出しの形式は確認中。音声なら「音楽＋カウント」を端末外のプレイヤーで使い、動画なら同じ音声に数字表示を付ける用途を想定する。ひちゃんから就寝中の作業継続を委任されたため、**最初にレビューできる実装は短区間の音声WAVを仮選択**し、動画は後段へ進める。返答があった扱いにはせず、商品全体を音声だけへ確定しない。UI表記は既存ルールに従い「ファイルに保存」とする。

- 入力は審査済み曲/revisionと拍地図、練習区間、速度、合図、反復回数、音量、利用可能な声、声のoffsetを固定したrender planとする。再生中の設定変更を出力途中に混ぜない。
- 実再生と同じ整数tick・transport・voice schedulerから出力する。書き出し専用の別BPM計算を作らない。速度を変えた音楽素材の遅延・拍地図対応も共通にする。
- 出力する声は標準音声と自分の録音を初期候補とする。v1の「受け取った先生の声は配り直せない」という境界を踏まえ、受け取った声を無条件で書き出しに含めない。先生の許諾と利用範囲の扱いを別途決める。
- 音声形式は、試作で検算できているWAVを技術基準とし、実用のMP3/M4A等は対象ブラウザの生成・再生・共有とcodec実装を評価して選ぶ。動画の場合は音声と表示の同一時刻基準、終端、codec、生成時間・容量も検証する。
- 保存前に長さと容量の見積り、進捗・中止・失敗時の再試行を用意する。長い音源の全bufferと出力を一度に持ってメモリ予算を超えないよう、分割render/encodeを検証する。今回の32秒OfflineAudioContext試作だけで全曲出力対応とはしない。
- 元曲/声/速度別素材の権利、加工・ファイル提供の範囲を確認してから商品に含める。Sunoの商用利用・正規download・加工/出自情報に関する条件は§6の規約確認を参照し、既存のアプリ内再生の承認だけで書き出しも許可済みとみなさない。
- 書き出したファイルはアプリの外に残り、lease期限や解約で再生停止・回収できない。販売する価値を「同期練習＋素材を作れること」とするか、出力の上限と生徒への配布をどう扱うかを、商品条件として決める。既存のアプリ内の先生向け共有ファイルへ楽曲を混入しない。
- 受入は、出力ファイルを別のプレイヤーで再生し、元の設定と音声・数字が一致すること、区間/反復/速度/合図/終端、onsetと混合ピーク、保存先からの再読込、処理中の中止、メモリ上限を確認する。

## 6. 曲メタデータと制作審査

現行TrackProfileは型だけだが、licenseがCC系に限定されている。Suno曲をCC0等へ偽装せず、版付きの曲catalog schemaを新設する。既存共有形式は変更しない。

```text
Track
  schemaVersion, trackId, revision, title, danceId, beatsPerBar
  asset: { assetId, sha256, codec, durationMs, sampleRate, channels, bytes }
  timing: { revision, referenceDownbeat, tempo, coverageStartTick, coverageEndTick }
  sections[]: { id, title, startTick, endTick, loopApproved, recommended }
  review: { timingStatus, danceStatus, reviewer, reviewedAt, evidenceRef }
  rights: { rightsRecordId, status, creditText, sourceUrl, allowedTerritories }
  publication: draft | reviewed | published | withdrawn
```

契約証跡は非公開のRightsRecordへ分離する。記録項目: 取得元／作者／曲ID・URL、生成日時・download日時、生成時／download時のプランと契約版、正規downloadの証跡、投入素材と声・歌詞の権利、Remix該当性、アプリ有料提供・加工・オフライン配信の許諾根拠、帰属・地域・期間・禁止事項、原本hash、確認者・確認日。課金カード・認証情報は記録しない。公開クレジットに契約・購入証明を載せない。

公開には`timingStatus=approved`、`danceStatus=approved`、`rights.status=approved`のすべてとhash一致が必要。曲の拍修正・差替えは新revisionにし、旧音源と新しいmapの混在を拒否する。権利撤回時は新規配信を停止し、オンライン端末へ失効版を通知する。既に渡したオフラインデータの即時回収は約束しない。

Suno規約の2026-09-03発効版を2026-10-23に確認。無料出力は非商用、Pro/Premierには権利移転条項があるが、商用利用には正規download等の条件もある。Remixには別の非商用制限があり、非侵害・著作権成立は保証されない。**この曲の生成・download時の契約と証跡は未確認なので、採用承認には使えない。** [Suno Terms](https://suno.com/terms)

## 7. PWAの最小有料構成

### 7.1 境界

```text
PWAの画面 → PracticeSession → 同じAudioContextの再生エンジン
                ↓ deps
     platform: 認証 / 利用権 / 配信 / 端末保存
                ↓ HTTPS
  認証済API → 購入・利用権DB → 非公開の楽曲object storage
                ↑
        決済事業者の署名付きwebhook
```

静的PWAだけで有料利用権を確定しない。最小サーバーは認証セッション、購入台帳、商品→権利の対応、配信許可、webhook検証を持つ。既存Cloudflare配信に同居できる構成を候補にするが、新規サービス契約・リソース作成は未実施。

| API案 | 役割 |
|---|---|
| `GET /api/me/entitlements` | サーバーで現在の権利を計算。更新時刻・有効期間・対象catalog・署名付きoffline leaseを返す |
| `GET /api/music/catalog` | 権利条件と公開状態を満たす曲のmanifest。公開用クレジットと非公開契約を分離 |
| `POST /api/music/access` | track/revision/chunkを検証し、短時間の取得権または認証済配信応答を返す。URLを知るだけで恒久取得できない |
| `POST /api/billing/checkout` | サーバー管理のproductIdから決済へ。価格・通貨・権利をクライアント申告で決めない |
| `POST /api/billing/webhook` | 署名・イベントID・順序を検証。重複配信に冪等。購入／更新／返金／失効の台帳を更新 |
| `POST /api/billing/reconcile` | 「購入を確認する」。サーバー側で決済記録を照合。戻りURLやスクリーンショットだけで権利を付けない |

PWAは外部checkoutから戻る前後で同じアカウントに購入を結び付ける。メール認証等の方式は未決。復元できる本人識別を設計してから販売する。webhook遅延は「購入を確認しています」と表示し、二重購入を促さない。Cookie認証ならHttpOnly/Secure/SameSiteと書込APIのCSRF対策、object配信には認可・URL期限・必要なCORSだけを設ける。秘密鍵と決済secretをクライアントへ出さない。

Web決済は現行PWAの候補。将来Capacitor化する場合のストア決済規則・地域条件は、その販売形態が決まった時点で公式規約を確認する。PWAでの購入方式をそのままストア版に持ち込めるとは設計上仮定しない。決済アダプタとentitlementを分ける。

### 7.2 権利状態

`unknown / active / grace / expired / revoked`を区別し、通信失敗をexpiredに変換しない。購入事実と「今この端末で鳴らせるか」は別状態。

サーバー台帳は`subjectId, productId, scope, validFrom, validUntil, status, revision`を持つ。買い切りの場合も対象曲／将来追加曲／再取得保証の範囲を商品条件で定義し、「永久に全曲」を暗黙に約束しない。

署名付きoffline lease案は`subjectId, installationId, scope/catalogRevision, issuedAt, expiresAt, entitlementRevision, keyId`。署名検証で改変を検知する。端末時計の後戻りを検知した場合はオンライン再確認へ戻すが、ブラウザ内に改変不能な時計・端末識別があるとは扱わない。

## 8. オフライン・復元・キャッシュと限界

- 有料音源を`public/`、dist、Workboxのprecache、公開Gitへ入れない。既存の無料標準音声precacheと容量上限を保持する。APIや署名URLに汎用CacheFirstを適用しない。
- ダウンロードは利用権確認→正しいrevisionの取得→hash検証→完了マーカーの順。部分保存は`ready`にしない。曲一覧の「端末にあります」は実物とmanifest両方を確認する。
- 専用保存領域は`subject/installation/track/revision`で分離する。通常HTTP cacheへ有料音源を残さず、アプリが選んだ保存領域だけに管理する。認証・利用権APIは`no-store`。
- 初版は明示的に準備した曲／区間だけをオフライン対象にする。保存前に容量見積り、失敗時に曲単位の削除・再取得を提供。使用中曲は自動削除しない。
- オフライン期限案は**最終確認から7日、かつ購入期間の終わりまでの短い方**。製品判断前の仮値で、購入前説明・実機検証後に確定する。lease期限が再生途中に来てもその1回は終わらせ、次のループ／再生を開始しない方針を候補とする。
- ログアウト時は全音停止→専用音源・lease・一時URLを削除／無効化し、他アカウントから再利用しない。削除が失敗した場合も復号／再生を許す状態を残さない。
- 再インストール／ブラウザ消去／別端末は、同じアカウントの購入をサーバーから復元し、音楽を再取得する。ローカルだけの録音とルーティンは別のバックアップ対象。Safariとホーム画面PWA間で保存が共有されることを前提にせず実機確認する。
- 保存の永続化要求は試せるが、ユーザーによる消去・容量制限・実装差をなくすものではない。[WHATWG Storage](https://storage.spec.whatwg.org/)
- 暗号化cacheを採用しても、再生のためにブラウザへ音と鍵を渡す以上、利用者による抽出や録音を完全には防げない。署名URLは配信制御、leaseは正規UIの期限管理でありDRMではない。強い複製防止を要求する楽曲は、このPWA構成では採用しない。
- 暗号化の具体方式は権利条件と実装費用を見て決める。採用する場合は端末ごとの鍵と版を管理し、logoutで削除する。非抽出WebCrypto鍵も悪意ある同一originコードによる復号を防ぐ保証とはしない。
- オフライン失効は即時に届かず、最大lease期間の遅延がある。権利者条件が即時停止を要求するなら、その曲はオンライン専用にする。

## 9. 音源サイズと全曲再生の段階

短いおすすめ区間は、制作側で元曲と対応の取れる別素材を作り、単独decodeできる形で配る。原本を無断で短縮置換しない。配信形式を圧縮してもdecode後のメモリが小さくなるとは限らない。

初期の設計予算案: 音楽の同時decode済みbuffer合計32MiB以内（声・一時bufferは別に計測）、1chunkを元曲30秒以内、現在＋次の最大2chunk。端末負荷を測って最終値を決める。全曲を一度decodeしてから切り分ける実装はこの予算を満たさない。

全曲を扱う次段では、制作側で連続するchunkとsource-time境界・hash・decode後sample数を用意する。圧縮encoder delay／paddingを含む境界を検証し、Web Audioの同じ時計へ次chunkを予約する。chunkを順につないだ音が元曲と拍位置・継ぎ目で一致することが条件。音楽だけが先へ進む／声だけ続く状態を作らず、次chunk不足なら全停止する。

ループの接続は承認区間ごとに短いfadeを検証する。fadeで拍位置や区間長をずらさない。自然に繋がらない場所は`loopApproved=false`にする。全曲・任意範囲・全速度を最初から対応済みと表示しない。

## 10. 実装の分け方と完了条件

| 段 | 作るもの | 次へ進む条件 |
|---|---|---|
| A: ローカル検証 | 原本hash・分析、短区間lab、元速度でclick／声との試聴、位相候補比較 | 測定値・再現手順・聞いた区間を記録。機械推定と人の承認を分ける |
| B: 共通transport | 曲用map（beatMapを含む）・範囲反復・逆写像・終端・先読み予約、既存Sessionの曲deps | 既存constantゴールデンとtiming基準が無変更で通る。曲用不規則map試験が通る |
| C: 端末内の縦通し | 1曲の短区間、曲選択、音量、合図、標準／録音の声、停止と中断 | 本物のブラウザで操作と録音を確認。iPhone／Androidの対象実機でメモリ・長時間ループ・Bluetoothを確認 |
| D: 有料基盤 | 商品決定後の認証・購入test mode・利用権・配信・復元・offline lease | 決済sandboxで購入／キャンセル／遅延／返金／別端末復元。未購入の直接取得拒否。既存PWA回帰 |
| E: 販売準備 | 楽曲審査、説明とクレジット、対象機種、運用と問い合わせ、撤回手順 | 価格・期間・offline条件・全権利証跡を承認。公開前の明示許可を得る |
| F: 追加希望の検証 | 全曲chunk再生、各種目約3曲の拍審査、範囲拡張、音程維持の速度変更、書き出し | 機能別の同期・音質・端末負荷・出力権利ゲートを通す。発売に含める範囲は商品判断で確定 |

曲なしの経路は現行の式・voice scheduling・goldenを維持する。曲ありのtransportを同じengineの明示的な分岐／協調部品として足す。共有できるvoice schedulerやsource停止は再利用するが、最初から大規模な統合リファクタはしない。

自動検証の重点:

- constant・非ゼロoffset・不規則beatMapで、範囲頭が0以外、半拍イベント、最終境界、複数周、0／1／2小節の合図を検証。単純な等間隔fixtureだけで非一定対応を通さない。
- `map → 逆map`の往復、絶対位置差、ループ10分以上の時刻非累積、倍率rの単位、音楽chunkの原点、声onsetを検証。
- engineの予約時刻誤差は計算上1 sample以内を目標とし、実音の同期・ダンスの拍同定とは別ゲートにする。
- 拍地図の審査案: 明瞭な拍の人手annotationに対して絶対誤差中央値20ms以内・95%点40ms以内を初期目標とする。曖昧な音の立上りは個別記録し、数値だけで合格にしない。冒頭／中盤／終盤で拍飛び・半倍・倍速・小節位相ずれがないこと。
- 音楽とcountの混合録音で区間先頭・末尾・ループ境界・短い分割拍を聴き、声の頭・クリック・clipを確認。Bluetoothの画面補正は表示だけに適用し、音楽／声の予約をずらさない。
- start直後のstop、準備中の曲変更、二重タップ、route移動、電話、バックグラウンド、自然終了、古いPromiseの解決で再生が復活しない。
- 権利なし／期限切れ／不明／失効を分け、通信障害時のlease、時計後戻り、アカウント変更、途中download、壊れたhash、旧mapとの混在を検証。
- SW更新中も練習を勝手に再読込せず、有料音源がdist／precache／共有ファイルへ入らない。旧SWからの更新・offline起動・キャッシュ消去後の復元を公開ビルド相当で通す。

実装段では`npm test`・`npm run typecheck`・`npm run build`・`npm run timing:compare`と該当smokeを実行する。今回の文書作成は実装完了や実機確認を意味しない。最終受入は「自動テスト」「本物のブラウザ実音」「対象スマートフォン」「音楽／ダンスの人手審査」「権利審査」を分けて報告する。

6. 対象端末と復元方法。PWA先行を続けるか、ストア販売も同時に必要か。
7. 書き出しは音声／数字付き動画／両方のどれか。形式・最大長・反復回数・利用できる声、生徒への配布範囲、出力回数の扱い。
